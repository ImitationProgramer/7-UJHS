# GuideSense 성동구 시설 기반 보행 경로 추천 PRD

작성일: 2026-10-09  
상태: 구현 전 초안 — 제품 방향 확정, 아래 기본값은 구현·API 검증 후 조정 가능  
범위: TMAP 보행 경로 후보를 성동구 횡단보도 데이터로 평가·추천하는 기능

## 1. 목적

시각장애인과 안내견의 이동을 지원하는 GuideSense에서, 출발지와 도착지에 맞춰 보행 경로를 조회하고 횡단보도 시설 조건을 반영해 추천한다.

성동구를 중심으로 일반 지도형 길찾기 화면을 제공한다. 사용자가 지도 또는 장소 검색으로 출발지·도착지를 직접 정하면 실제 TMAP 경로를 조회한다. 성동구 횡단보도 시설 데이터를 추가해 신호등 조건을 적용하고, 음향신호기·점자블록·보도턱 낮춤과 거리 정보를 비교해 시각장애인에게 필요한 경로 선택 근거를 제공한다. 추천은 확보한 후보와 2022년 시설 데이터 기준의 결과이며 현장 안전을 보장하는 안내가 아니다.

## 2. 이번 구현 범위

### 포함

- 제공 CSV 로드·검증 및 횡단보도 시설 조회.
- 성동구 중심의 이동·확대·축소 가능한 지도와 서비스 지역 표시.
- 지도에서 지점을 선택해 출발지 또는 도착지로 지정.
- 장소 검색 결과에서 출발지·도착지 선택 및 두 지점 교환·변경.
- 서버측 TMAP 보행자 경로 요청과 후보 중복 제거.
- 경로의 실제 횡단 구간과 공공데이터 레코드 연결.
- 신호등 없는 횡단보도를 건너는 후보 제외.
- 조건을 통과한 후보의 시설·거리 비용 계산 및 추천.
- 기존 대시보드에 지도·경로·추천 이유·후보별 판정 표시.
- 선택된 경로를 따라 이동하는 시뮬레이션과 구간 시설 안내.
- 기존 User Brooch Output에 경로 요약 및 시뮬레이션 구간 안내 텍스트 연결.
- LIVE SENSOR / DATASET REPLAY 기존 동작 보존.

### 제외

안내견 멈칫·정지·방향 전환 탐지, 행동 모델 변경·재학습, 개인화 학습, 이동 이력 저장, 케어 추천, OpenAI/LLM 연동, 음성 입출력, 카메라, 진동, 실제 GPS 기반 자동 턴 안내, 자체 보행 그래프 탐색, 전국 데이터 연동.

이번 시설 비용 계산은 규칙 기반이다. 이를 학습 AI라고 표현하지 않는다. 안내견 분석과의 연결은 다음 단계다.

## 3. 사용자 흐름

1. 사용자가 성동구 중심의 지도를 열고 이동·확대·축소하며 장소를 확인한다.
2. 지도에서 지점을 선택해 ‘출발지로 지정’ 또는 ‘도착지로 지정’한다. 장소 검색 결과에서도 같은 동작을 제공하며, 선택한 두 지점은 마커와 입력란에 표시한다.
3. ‘길찾기’를 누르면 서버가 TMAP 경로 후보를 조회한다.
4. 시스템이 중복 후보를 제거하고 횡단보도 연결·제외·비용 평가를 수행한다.
5. 추천 가능한 후보가 있으면 지도에 추천 경로를 표시하고 이유를 설명한다. 다른 후보의 거리·시설·판정도 볼 수 있다.
6. 추천 가능한 후보가 없으면 제외 또는 미확인 이유를 표시한다. 조건을 자동 완화하지 않는다.
7. 추천 경로에서 ‘이동 시뮬레이션’을 시작하면 위치 마커와 진행 구간이 변하고 대응하는 횡단 시설 정보를 안내한다.

경로가 실제로 서로 다르지 않을 수 있으며 시설이 더 좋은 대안이 항상 존재하는 것도 아니다. 시연 결과를 만들기 위해 불리한 후보나 실패를 숨기지 않는다.

## 4. 데이터 계약

### 시설 데이터

사용자 제공 파일: `서울특별시 성동구_횡단보도_20221215.csv`.

직접 확인 결과: CP949, 987행, 모든 행 기준일 2022-12-15. 보행자신호등 Y/N=272/715, 음향신호기 207/780, 보도턱 낮춤 932/55, 점자블록 871/116. 좌표는 모든 행 숫자 파싱 가능. 이는 파일 확인 결과이며 현장 검증은 아니다.

정규화 필드: 횡단보도 ID, 경도·위도, 기준일, 차로수, 보행자신호등·음향신호기·보도턱 낮춤·점자블록 유무, 원본 식별 정보.

- 유무는 `yes / no / unknown`으로 표현한다. 빈 값이나 예상하지 못한 값은 no로 바꾸지 않는다.
- 좌표계는 값 범위 및 제공 메타데이터를 확인해 사용한다. 경도·위도 순서를 테스트한다.
- 중복 좌표·ID와 상충하는 시설 값은 감사 결과에 표시하고 확정 연결에 사용하지 않는다.
- 데이터 범위 밖이나 레코드가 없는 곳은 ‘시설 없음’이 아닌 ‘미확인’이다.
- 보도턱 낮춤 유무는 실제 턱 높이나 일반 문턱 측정값이 아니다.

### 출발·도착지 입력과 서비스 지역

출발·도착은 사용자가 선택한 좌표·표시명·선택 출처(지도 또는 검색 결과)로 관리한다. 사전 장소 목록으로 제한하지 않는다. 검색 결과는 동명이소를 구별할 수 있도록 주소를 표시한다. 지도 선택 시 좌표에 임의의 장소명을 붙이지 않고 이름을 확인할 수 없으면 ‘지도에서 선택한 위치’로 표시한다.

초기 서비스는 성동구로 제한한다. 행정구역 경계 또는 신뢰할 수 있는 주소·지역 판별 수단을 확보하고 서버에서도 범위를 검증한다. CSV 좌표의 최소·최대 범위를 성동구 경계로 대신 사용하지 않는다. 선택 지점이 범위 밖이거나 지역을 확인할 수 없으면 위치를 다시 지정하도록 안내한다.

두 지점이 같거나 미입력인 경우 길찾기를 실행하지 않는다. 지도에서 선택한 좌표가 보행 접근 불가능하거나 TMAP이 경로를 만들지 못하면 사용자에게 위치 조정을 요청한다. 출발·도착이 성동구 안이어도 경로 전체에 시설 정보가 있다는 뜻은 아니므로 경로 단위의 미확인 정책을 적용한다.

## 5. TMAP 후보 생성

서버에서 같은 출발·도착지에 대해 `searchOption` 0(추천), 4(추천+대로우선), 10(최단), 30(최단거리+계단제외)을 요청하는 방식을 초기 후보 생성 전략으로 사용한다. 실제 지원·응답 구조는 앱키로 확인한다.

- 경로 좌표, 거리·시간, 안내 지점을 내부 표준 타입으로 정규화한다.
- 동일 경로는 좌표 정밀도 정규화와 안내 순서에 근거해 중복 제거한다. 유사하지만 횡단 구간이 다른 경로를 합치지 않는다.
- 단일 옵션 실패 시 성공한 후보는 유지하고 누락된 옵션과 오류를 표시한다.
- 옵션별 결과가 모두 같으면 단일 후보로 평가한다. 대안을 만들어 표시하지 않는다.
- 경유지를 이용한 추가 후보 생성은 이번 기본 범위에서 제외한다. 첫 API 조사에서 후보 확보가 크게 제한되면 별도 범위 변경으로 검토한다.
- 후보 없음과 추천 불가를 구분한다.

TMAP에 시설별 가중치를 전달하는 방식이 아니다. TMAP이 만든 후보 안에서 평가·선택한다. 전체 보행 네트워크의 최적 경로라고 주장하지 않는다.

## 6. 횡단보도 연결 — 구현의 핵심 검증 항목

가까운 시설 점을 경로에 붙이는 것만으로 ‘실제로 건넌다’를 확정하지 않는다.

1. TMAP 응답의 안내·기하 정보를 조사해 횡단 이벤트를 식별한다.
2. 해당 이벤트의 위치·횡단 선형과 CSV 좌표의 공간 관계를 비교한다.
3. 연결 결과를 `matched / ambiguous / unmatched`로 분류하고 근거를 남긴다.
4. 교차로에 여러 횡단보도가 가까이 있거나 위치가 모호하면 확정하지 않는다.
5. 시설 미확인과 API 횡단 정보 부족을 별도로 표시한다.

연결 거리 임계값은 실제 응답 및 CSV 분포를 확인한 뒤 정한다. 임의의 숫자를 안전 검증 기준으로 사용하지 않는다. ‘횡단 이벤트 0개’와 ‘API에서 횡단 정보를 식별하지 못함’을 구분한다.

**착수 검증:** 실제 TMAP 샘플에서 횡단 구간을 충분히 식별할 수 있는지 먼저 확인한다. 부족하면 시설 비교는 미확인 상태로 표시하고 추천 가능으로 승격하지 않는다. 추가 도로 연결 데이터가 필요한 경우 한계를 보고한다.

## 7. 제외 정책

| 후보 상태                                                         | 처리                   |
| ----------------------------------------------------------------- | ---------------------- |
| 실제 횡단으로 연결된 시설 중 보행자신호등=no가 하나 이상          | 제외                   |
| 신호등 부재는 확인되지 않았지만 횡단 식별·연결·신호등 값이 미확인 | 미확인, 추천 대상 제외 |
| 횡단 식별이 가능하고 모든 횡단의 신호등=yes                       | 평가 가능              |
| 횡단이 없는 경로로 확인됨                                         | 평가 가능              |

신호등 없는 횡단보도는 큰 감점이 아닌 필수 제외 조건이다. 후보의 일부가 성동구 데이터 범위를 벗어나도 정보가 부족한 횡단을 yes로 간주하지 않는다.

조건을 충족한 후보가 없으면 “조회한 경로 후보에서 신호등 조건을 확인한 추천 경로를 찾지 못했어요”라고 표시하고 후보별 이유를 제공한다. API 실패와 이 결과를 혼동하지 않는다.

## 8. 비용과 추천 — 초안 기본값

제외·미확인 후보를 제거한 뒤 낮은 비용의 후보를 선택한다. 아래 값은 데모용 설계 기본값이며 사용자 연구나 현장 검증으로 얻은 위험도 계수가 아니다.

`비용 = 거리(m) + Σ 횡단보도 시설 페널티`

| 해당 횡단보도 항목 |   no | unknown | yes |
| ------------------ | ---: | ------: | --: |
| 음향신호기         | +300 |    +300 |  +0 |
| 보도턱 낮춤        | +150 |    +150 |  +0 |
| 점자블록           | +100 |    +100 |  +0 |

unknown은 실제 부재로 설명하지 않는다. 같은 비용 처리는 정보가 불충분한 후보를 유리하게 만들지 않기 위한 초안 정책이다. 신호등 unknown은 앞 단계에서 추천 제외한다.

- 페널티는 거리와 비교하기 위한 비용 단위이며 실제 추가 거리나 사고 위험 수치가 아니다.
- 동일 횡단 이벤트의 중복 레코드를 중복 과금하지 않는다. 별개의 실제 횡단은 각각 반영한다.
- 동률이면 거리, 예상 시간, 후보 ID 순으로 선택한다.
- 차로수·스마트횡단보도는 표시만 하고 이번 초기 점수에는 넣지 않는다.
- 가중치는 서버 설정 한 곳에 보관하며 응답에 평가 정책 버전을 포함한다.
- 추천 이유는 실제 비교 결과로 생성한다. “다른 평가 가능 후보보다 음향신호기 없는 횡단이 적어 선택됐어요” 같은 근거가 있을 때만 표현한다.
- 가중치 때문에 긴 경로가 선택되면 최단 평가 가능 후보 대비 추가 거리·시간을 함께 표시한다. 최대 우회 제한은 이번 초안에 포함하지 않으며 검증에서 지나친 우회가 발견되면 정책을 재검토한다.

## 9. 화면 및 시뮬레이션

기존 Dashboard에 별도 Navigation 영역을 추가한다. LIVE/REPLAY와 시뮬레이션 위치의 출처를 분리한다.

필수 화면:

- 성동구 중심의 지도, 확대·축소·이동, 서비스 지역 표시.
- 출발·도착 검색 입력, 검색 결과·주소, 지도에서 지정, 마커, 두 지점 교환, 길찾기 버튼.
- 지도 클릭에만 의존하지 않는 키보드 조작 가능한 검색·결과 목록과 텍스트 경로·시설 안내.
- 조회 상태와 옵션별 실패 정보.
- 지도상 후보·추천 경로 및 횡단 시설 위치.
- 후보별 거리·시간, 제외/미확인/평가 가능 판정, 시설 집계, 비용 내역.
- 추천 이유와 추가 거리·시간.
- 데이터 기준일, ‘시설 데이터 기준 추천’, ‘이동 시뮬레이션’ 표시.
- Play / Pause / Restart, 경로 진행률과 현재 안내.

시뮬레이션은 선택 경로의 좌표와 길이를 따라 이동한다. 안내 지점·횡단 이벤트를 통과할 때 해당 설명을 갱신한다. 실제 GPS나 안내견 이동으로 표시하지 않는다. 목적지 변경·새 조회·추천 경로 변경 시 이전 시뮬레이션과 안내를 중지·초기화한다. 경로 조회에 실패한 뒤 이전 경로가 새 결과처럼 남지 않는다.

## 10. 내부 인터페이스 초안

기존 코드 규칙을 확인해 최종 명칭을 조정한다.

- `GET /api/navigation/search`: 검색어에 대한 장소·주소·좌표·지역 확인 상태 반환. TMAP POI 연동은 서버에서 수행한다.
- `GET /api/navigation/metadata`: 서비스 지역과 시설 데이터 기준일·평가 정책 정보 반환.
- `POST /api/navigation/routes`: 사용자가 선택한 출발·도착 좌표·표시명을 받아 범위 검증 후 후보 조회·시설 연결·평가 결과 반환.

응답 구성: 요청 ID, 출발·도착, 데이터 기준일, 평가 정책 버전, 옵션별 오류, 후보 목록, 추천 후보 ID 또는 null, 전체 결과 상태.

각 후보: 출처 옵션, 기하·안내, 거리·시간, 횡단 이벤트와 연결 상태, 시설 집계, 판정·사유, 평가 가능 시 비용 내역.

시뮬레이션은 프런트에서 수행하고 실제 센서 WebSocket 프레임을 생성하지 않는다. TMAP 앱키는 서버 환경변수에만 둔다. 원본 API 응답은 필요한 내부 타입으로 변환하며 오류 메시지·로그에 앱키를 포함하지 않는다.

## 11. 구현 소유 경계

이번 담당자는 Navigation 백엔드 모듈·CSV 어댑터·평가 로직·Navigation UI·시뮬레이션·관련 테스트와 문서를 소유한다.

팀원의 모바일 센서 수집, 캡처, LIVE/REPLAY 프로토콜, Replay 추론, 모델·메타데이터는 변경하지 않는다. `main.py`의 라우터 등록과 `App.tsx`의 화면 연결처럼 공유 진입 파일은 필요한 최소 통합만 수행하고 변경 내용을 공유한다. 기존 Brooch 출력에는 출처와 활성 기능을 명시해 Replay 예측과 경로 안내가 섞이지 않게 한다.

## 12. 검증 및 완료 기준

- CSV 987행·필드·유무·좌표 파싱 검증과 중복·상충 감사 결과를 남긴다.
- 지도 지정과 장소 검색 각각으로 출발·도착을 선택하고, 마커·입력란·요청 좌표가 일치하는지 확인한다.
- 동명이소 선택·두 지점 교환·미입력·동일 지점·성동구 밖·지역 확인 불가·접근 불가 지점을 처리한다.
- 키보드로 검색·선택·길찾기·결과 확인이 가능하고 추천 판정을 색상에만 의존하지 않는다.
- 실제 TMAP으로 서로 다른 최소 5개 출발·도착 쌍의 응답을 확인한다. 결과가 추천·미확인·제외 중 무엇이든 그대로 기록한다.
- 후보가 중복될 때 한 번만 평가하고 부분 API 실패를 표시한다.
- 신호등=no인 실제 횡단이 포함된 후보는 거리와 무관하게 제외된다.
- 연결 불확실·시설 누락·횡단 식별 실패 후보는 추천되지 않는다.
- 경로 옆 횡단보도를 실제 횡단으로 잘못 연결하지 않는 사례와 밀집 교차로 사례를 검사한다.
- 시설·거리 조건이 다른 고정 입력으로 가중치에 따라 선택이 달라짐을 검증한다. mock 검증과 실제 TMAP 결과를 구분한다.
- 후보 없음·전부 제외·전부 미확인·키 없음·인증/쿼터/timeout·잘못된 응답을 구분해서 처리한다.
- 실제 브라우저에서 지도/검색으로 출발·도착 지정→길찾기→후보 비교→시뮬레이션→출발지 변경을 확인한다.
- 기존 LIVE/REPLAY의 관련 회귀 검증을 통과한다.
- 실제 API 결과, mock 테스트 결과, 미검증 한계를 구분해 보고한다. 앱키가 없으면 실제 연동 완료로 선언하지 않는다.

추천 알고리즘의 검증은 규칙 준수·선택 결과·연결 정확성에 초점을 둔다. 실제 이동 안전성·사용자 만족·건강 케어 효과 검증은 이번 완료 기준에 포함하지 않는다.

## 13. 구현 순서 및 남은 기술 확인

1. 최신 저장소와 실행 환경, 앱키, 기존 Dashboard 및 출력 계약 확인.
2. CSV 감사 및 실제 TMAP 응답 조사. 횡단 식별·공간 연결 가능성을 먼저 확인.
3. 서버 후보 생성·중복 제거·판정·평가 구현과 의미 있는 단위 테스트.
4. 지도·장소 검색·출발/도착 지정·후보 비교 화면 및 시뮬레이션 구현.
